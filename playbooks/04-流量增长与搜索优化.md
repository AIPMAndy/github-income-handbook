# 实操手册 04：让 GitHub 项目开始被真实用户搜索到

## 基本原理

搜索用户往往带着问题来：他们会搜“论文三线表自动排版”“免费 AI API 怎么找”“Agent 本地运行报错”，很少搜你给项目起的玄学代号。

## 第一步：提取问题关键词

建立一个词表（每个词都与实际内容匹配）：

| 搜索意图 | 示例关键词（仅为候选词，未声明真实搜索量） | 页面应提供 |
| --- | --- | --- |
| 入门教程 | GitHub Pages 404 怎么办 | 原因与逐步排查 |
| 使用工具 | 本地 AI 工具安装教程 | 前置条件和命令 |
| 对比选择 | GitHub Sponsors 和赞助区别 | 地区/资格/政策 |
| 错误解决 | workflow failed permissions pages | 准确报错与对应处理 |

你不能只把词塞进标题，必须真的有解决方案。

## 第二步：优化仓库首页

1. 仓库标题：简短、可读、不要标题党。
2. Description：第一句话写清楚服务谁、解决什么。
3. README 首屏：一句价值 + 一个真实效果 + 最小上手说明。
4. 目录：从“从零开始”“教程”“模板”“FAQ”自然分层。
5. 真实外链引用：附官方文档和日期，提高可验证性。
6. 可维护状态：明确项目适配版本和最后校验日期。

## 第三步：内容分发，以解决问题为单位

一周可以试三个角度：

- 痛点：我为什么花两个小时改论文格式？
- 演示：这是一次实际运行/使用的全过程。
- 教程：别人最容易卡在第 3 步，我把排查写出来了。

小红书、B 站、Threads、X、公众号内容应改写为各平台原生表达，并遵守具体平台导流规则。不要跨平台批量粘贴同一条广告，更不要给陌生人强推。

## 第四步：测量，不要被 Star 误导

仓库的 **Insights → Traffic** 提供最近 14 天的访客数据及部分来源。不是无限期历史报表。每周在固定日期记录一次滚动访客值、仓库访问来源、询盘来源、报价、成交和回款。

**严格避免：** 直接把连续两周的“过去 14 天独立访客”求和，当成不重复的月访客；有重叠会重复计数。

## 第五步：回到收入验证

你可能拿到 1000 次访问，却没有一个明确目标客户。那代表流量质量或服务边界有问题；不是换个更大的 Banner 就能解决。

反过来，你可能只有几十个访问，却有 2 个具体企业部署咨询。优先把流程跑通，让交付标准化，而不是盲目冲榜。

**30天停止/转向条件样例（需按业务自定）：** 连续多次访谈找不到实际痛点、没有人能复现 Demo、主要评论集中在没有需求的围观者、付费交付成本明显超过回款。
