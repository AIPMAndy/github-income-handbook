# 实操手册 08：把工程五步法用于 GitHub 赚钱

目标：降低无效努力，提高真实商业反馈密度。

## 一、质疑每个需求

问题：**“项目一定得有 1000 个 Star 才能收钱”从哪儿来的？**

答案：不成立。先问谁需要什么结果、现在付出了多少成本，是否真愿意为你这项具体交付买单。删除没有证据的前提。

## 二、删掉多余的路径和功能

常见坏策略：同一天做三套教程、上线五个工具、同时做赞助+广告+课程+SaaS。你可能会拥有更多仓库，却没有任何一个产品的付费验证。

行动：只保留你最能稳定交付、最贴近真实付费问题的一个方向。其他都进入“停止做清单”。

## 三、简化并优化链路

把“关注公众号 → 私信 → 进群 → 加微信 → 付费沟通 → 再卖服务”缩短为：**开源样例公开可用 → 用户主动看服务范围 → 简短需求确认 → 清晰报价与验收**。

极力避免以技术噱头代替用户可理解的价值。

## 四、加快反馈周期

每周只做一次最小实验：一位真实使用者复现、一份有效询盘、一张明确拒绝理由、一份实际成本表。用证据决定下一周做不做。

## 五、最后才自动化

有成功交付并且流程稳定后，再用 AI 自动化文档整理、测试、FAQ 分类和周报。客户隐私必须脱敏，合规授权必须明确。

**自动化放在第五步**：错误流程自动化，只会放大损失和风控风险。

## 对抗式结论

没有需求：停止建功能。  
没有信任：补完整演示与 README。  
没有询盘：调整受众与可发现性。  
没有成交：检查交付内容、付费意愿与定价。  
没有利润：停止扩张，修复单位经济。
